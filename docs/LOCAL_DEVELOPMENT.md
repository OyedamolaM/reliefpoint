# Local sign-in

The development server uses `http://localhost:3000`. It loads server configuration from the ignored `.env.local`; nothing in that file should use a `VITE_` prefix or be committed.

1. Copy `.env.example` to `.env.local` if the local file does not exist. Keep `APP_ORIGIN=http://localhost:3000`. Set `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` from the same Supabase project. Use a separate staging project for development when possible, with all migrations applied.
2. Generate a local `SESSION_SECRET` with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` if it is blank. Local session/MFA cookies are separate from the production hostname. Leave payment/email keys blank unless deliberately testing those services; never use a live payment key for local checkout tests.
3. Run `bun run dev`, then open `http://localhost:3000/admin` for administration or `http://localhost:3000/account` for the customer interface. The server refuses a different port so the configured request origin remains exact. Restart the process after changing local configuration.
4. Sign in with an existing verified account in that Supabase project. Staff need an assigned role and their normal authenticator code. A new customer account uses normal registration and email verification, with no staff role. Use separate browser profiles or an incognito window to test staff and customer accounts simultaneously.
5. For local registration confirmation, add `http://localhost:3000/api/auth/callback` to the project's Supabase Auth redirect allowlist. Keep the production Site URL and redirect entries intact if this is a shared project. Existing verified accounts can sign in locally without sending a new confirmation email. Email recovery/invitation templates that use `.SiteURL` continue to open the project's configured Site URL; use a separate staging project to test those full email flows locally.

Missing credentials do not enable a fake admin or customer login. `/admin` uses the same permission and MFA checks locally as in production. A production account is available locally only when both environments connect to its Supabase project. Changes made against a shared project affect that project's real data; a different browser does not isolate its database.

Session checks do not clear an already signed-in interface for temporary network/provider failures. A retry toast is shown once per failure period. The API still verifies every protected request and refuses access while verification is unavailable. Missing/revoked sessions and the configured 24-hour staff / 72-hour customer inactivity limits still end access, with a seven-day absolute maximum. Overlapping browser session checks share one request, and late responses cannot restore an account after sign-out.
