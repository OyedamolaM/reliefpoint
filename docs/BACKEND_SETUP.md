# Backend setup and launch

The backend is implemented on `feat/reliefpoint-backend`. This document does not authorise a push or deployment. Use a separate Supabase project and Paystack test key for staging. No credentials are included.

## Configure

For localhost credentials, staff/customer sign-in and redirect settings, see [LOCAL_DEVELOPMENT.md](LOCAL_DEVELOPMENT.md).

1. Copy `.env.example` to `.env.local`. Set the exact trusted `APP_ORIGIN` (HTTPS in production), Supabase URL/anon/service-role keys, independently generated session/worker secrets, Paystack secret key and Brevo API key. None uses a `VITE_` prefix. Never put the service-role key in client code.
2. Apply the SQL files in `supabase/migrations` **in filename order**, using the Supabase SQL editor or your migration runner. Back up an existing database first. These migrations create new tables; do not run against an unrelated project.
3. In Supabase Auth, enable email confirmation, email/password login and TOTP MFA. Disable anonymous sign-in. Set Site URL to `APP_ORIGIN`, allow `${APP_ORIGIN}/api/auth/callback` and `${APP_ORIGIN}/api/auth/callback?recovery=1`, and remove unused redirect URLs. Turn on leaked-password protection if available on your plan. Require at least 10 characters. The app enforces its own idle/absolute session limits independently of Supabase subscription features.
4. Configure Brevo custom SMTP in Supabase: `smtp-relay.brevo.com`, port 587, your Brevo SMTP login and **SMTP key**, sender `support@reliefpointpharmacy.com`. The SMTP key is different from the transactional API key. Verify your sender/domain and publish Brevo's SPF/DKIM records plus the business's DMARC policy. Test confirmation and password recovery on the final domain.
5. Set the Supabase recovery email template link to `{{ .SiteURL }}/api/auth/confirm?token_hash={{ .TokenHash }}&type=recovery`. The callback verifies the recovery token with Auth before permitting password changes without the old password. Normal confirmation uses PKCE through `/api/auth/callback` and should be opened in the browser that began registration.
6. Register and verify the initial owner normally. Provision their role once using the trusted SQL editor: `insert into public.staff_roles(user_id, role) values ('VERIFIED-AUTH-USER-UUID', 'owner');`. Sign in at `/admin`, enroll TOTP, then verify it. Public registration never assigns roles. Owners/admins can manage non-owner staff; only owners can grant owner access or change an owner's roles. Staff cannot remove their own access.
7. Configure Paystack's webhook URL as `${APP_ORIGIN}/api/payments/webhook`. Callback URL is supplied by the server. Enable the supported Nigerian card, bank-transfer and USSD channels. Confirm the domestic fee schedule against your actual Paystack account before enabling checkout; international cards require a separately reviewed fee policy. Do not enable live keys until the launch checklist passes.
8. Schedule a POST to `${APP_ORIGIN}/api/internal/worker` every minute with `Authorization: Bearer WORKER_SECRET`. Use Supabase Cron + pg_net, storing the URL/secret in Supabase Vault, or an equivalent authenticated scheduler. Never put the secret in a public URL. This job is required for durable webhook verification, payment recovery, reservation expiry, refund reconciliation, email retries and prescription retention. Monitor failures and the pending queue age. A failed job safely retries; uncertain refunds are never submitted twice automatically.

The app is ready for frontend preview without credentials. It does not fabricate accounts, orders or successful payments. Connecting a configured project switches the storefront to the database catalog; it does **not** seed unverified live stock. Add products/photos and actual stock batches in administration.

## Operations

Apply `202611250004_staff_access.sql` before using Settings → Staff access → Add staff. Enter the name, email and role. Existing accounts must already have verified email; new accounts receive the configured Supabase invitation email. Staff must set a password and complete MFA before protected administration is available. The server rate-limits invitations. Role changes and their audit records commit together in a service-only RPC that independently checks the actor's database role, protects owner access and rejects self-removal. An email sent before a failed role grant is reported as incomplete rather than a successful staff setup.

Optional environment-managed **owner recovery** uses both `SUPPORT_USER_ID` and `SUPPORT_EMAIL` in server configuration (Vercel and/or ignored `.env.local`). Apply `202611260001_owner_recovery.sql` first. Register the recovery account normally and verify its email; take its immutable ID from Supabase Auth. Both ID and verified email must match. Empty/mismatched values grant nothing. Sign in normally, enroll an authenticator if needed, and verify its code. Normal session limits and 24-hour MFA verification still apply; password-recovery sessions cannot restore owner access.

After verified MFA, a service-only RPC rechecks the active session, verified email and hashed MFA grant, then restores a real `owner` database role and records `environment_owner_recovered` atomically. This permits full administration, including staff and owner management, using the same permissions as other owners. Existing pharmacist-only clinical sign-off requirements remain. It is an audited recovery mechanism, with no public support switch or shared secret password. Configuration values stay on the server. The restored owner appears in Staff access and audit records.

**Revocation:** removing either environment value prevents future recovery, but does not delete an owner role already restored. Remove both values and redeploy/restart first, then use another owner or trusted SQL Editor to remove the recovery account staff roles, revoke its Auth sessions and delete its remembered MFA grants. Leaving recovery enabled allows the account to restore its own owner role again. Keep this account private and protect its mailbox and authenticator. Never use a customer account as the recovery identity.

If administration reports a loading error, run the read-only `supabase/operations/verify-admin.sql` in the correct project's SQL Editor. Missing Orders/Customers functions require `202611250003_admin_directory_search.sql`. If those functions exist but the API still returns `PGRST202`, refresh PostgREST's schema cache with `NOTIFY pgrst, 'reload schema';`. Delivery reads `shipping_zones` directly and does not depend on that migration. Inspect redacted Vercel `admin_data_failure` logs by request ID for other database failures; logs contain only the resource and provider error code, never query text, customer details or credentials.

If unsure whether the release's migration was applied, `supabase/operations/repair-admin-loading.sql` safely installs or replaces the **202611250003** functions, restores service-role delivery read access, reloads the API schema cache, and returns the setup checks. It does not delete records or enable checkout. This repair belongs to that release: review later function migrations before reusing it on a future version. If all checks pass but Delivery still fails, inspect its private API request ID and the corresponding `admin_data_failure` resource/code rather than guessing a schema change.

Apply `202611250003_admin_directory_search.sql` before releasing the customer directory and expanded order search. These RPCs are executable only by the service role, behind the existing staff/MFA checks. They return 24-row pages and omit payment secrets and prescription file paths. Order searches include immutable purchased-item names, reference and customer contact details; date ranges use Nigeria time and include the chosen end date. Orders and pending payments remain separate. Customer addresses use saved addresses or the latest verified order; email comes from Supabase Auth.

Customer invitations use Supabase Auth SMTP, not a locally assigned password or auto-confirmed account. Configure the **Invite user** email template link as `{{ .SiteURL }}/api/auth/confirm?token_hash={{ .TokenHash }}&type=invite`, with Site URL set to the canonical app origin. The server consumes the invite token, establishes HttpOnly cookies and opens password setup; no tokens are placed in browser storage. Invitations require owner/admin/support permission, staff MFA and rate limits. Verify this email template and actual SMTP delivery in staging before using Add customer. Existing accounts must sign in or recover their password; invitations never overwrite their credentials. Provider acceptance means sent, not guaranteed delivery.

Product imports accept JSON files up to 10 MB, processed sequentially in batches of 20 with per-row errors and progress. The API accepts at most 20 records per request and rate-limits staff import requests. It does not automatically repeat an uncertain batch: review the product list after an interrupted request to avoid duplicate creations. Large imports may need to wait for the rate-limit window before continuing; use exported stable product IDs for updates.

If a buyer sees checkout unavailable, open **Admin → Settings → Business & checkout → Checkout status**. The administrator-only checklist identifies the checkout switch, Paystack mode and any missing live-launch requirements without exposing credentials. Save settings and select **Recheck**. A test key requires checkout enabled; a live key additionally requires all approved launch settings, email/worker configuration and a worker heartbeat within ten minutes. Quotes now check readiness before payment review; payment initialization and the database transaction continue to enforce their own launch checks. This configuration checklist does not certify that a provider account can send emails or settle payments: verify those services separately.

Apply `202611250002_mfa_browser_grants.sql` before deploying the session/MFA changes. Customer inactivity expires after 72 hours and staff inactivity after 24 hours. Both retain a seven-day absolute session maximum. Account activity syncs on interaction at most once every five minutes; inactive tabs do not send keepalive polling. Supabase Auth time-box/inactivity settings must allow these durations as well, or the provider will end sessions earlier.

Authenticator enrollment is once per account. A successful code creates a non-sliding 24-hour browser grant, held as an opaque, host-only Secure/HttpOnly/SameSite cookie and a hashed, user/factor-bound database record. No grant is created merely because an existing JWT is `aal2`. Existing enrolled staff enter a code once after deploying this feature. The API exposes a separate `mfaVerified` flag and expiry; it never rewrites Supabase assurance claims. Server staff authorization checks this grant on every request, including its expiry and the factor's current verified status. Direct Supabase RLS policies continue to require actual `aal2` and do not gain a trusted-browser bypass.

Ordinary sign-out ends that session but preserves the remaining browser-verification window. Sign out all devices, password changes and completed password-recovery links revoke remembered browsers. Removed authenticators invalidate their grants immediately. The worker cleans expired grants; expiry is enforced even if the worker is unavailable. A different browser/device needs its own code.

Apply `202611250001_product_pricing_sales.sql` before deploying the optional product prices and dashboard period filters. Regular, discount and staff-only cost prices are stored in integer kobo. A blank discount restores the regular price; a blank cost remains unset. Catalog filtering, quotes and checkout snapshots use the discounted selling price when supplied; existing order snapshots remain unchanged. The catalog view excludes cost prices.

Dashboard sales use verified payment timestamps in Nigeria time, with Monday-based weeks and inclusive custom end dates. Confirmed sales retain the existing gross-charge definition (delivery and customer processing fees included; fully refunded orders excluded). Confirmed-order counts include refunded orders; prescription and pending-payment queues always show current totals. The database returns aggregates rather than downloading orders for calculation.

For the one-time Vault and Cron setup, follow [WORKER_SETUP.md](WORKER_SETUP.md) and run `supabase/operations/schedule-worker.sql`. This operational script is separate from schema migrations and does not enable checkout.

- `/account`: profile, saved addresses, orders/prescriptions, password and MFA settings. Guest tracking requires matching reference/email and an expiring email link. Verified customers can claim matching-email guest orders.
- `/admin`: products, categories, stock, delivery zones, orders, prescriptions, refunds, inbox, Health Tips, staff access, settings, provider events and audit history. Staff must complete MFA for every protected administrative endpoint.
- Upload JPEG/PNG product and article photos from the device. They go directly into private quarantine through scoped upload tickets, then the server validates them and creates stripped, compressed WebP variants. This supports the advertised file sizes without routing large browser requests through Vercel. Prescriptions accept PDF/JPEG/PNG (5 MB) in a separate private bucket; authorised downloads are audited and expire after 60 seconds. The public media bucket must **never** contain patient documents.
- Paid prescription orders stay on hold until approval. Rejected prescriptions need a cancellation/refund decision; money is not silently returned or retained. No substitutions are made automatically. Do not restock returned medicines without pharmacist approval.
- Pending payments remain pending until verified with Paystack. Amount/currency/environment mismatches stay in an exception queue. Use order reconciliation rather than requesting another payment. Live checkout requires a successful worker run within the preceding ten minutes; losing mail/worker configuration prevents new live checkouts without blocking reconciliation of existing payments.
- Refund submission is an idempotent, durable request. Worker/provider results determine final status. A network timeout leaves the refund processing; reconcile against Paystack before any manual retry. Provider fees are recorded separately from the customer fee. Choose a test refund-fee policy in staging before exercising refunds; production policy approval remains a separate launch requirement.
- Email contains status notifications and secure links, not prescriptions or medication details. Operational emails retry with backoff; failed messages can be retried in administration.
- Catalog queries project only displayed fields, use 24-item pages and indexed search. Public API responses have short CDN caching; customer, staff, prescription and payment responses are `no-store`. Public changes may take a few minutes to reach an existing CDN cache. Browser data is reused for five minutes by default. No Realtime subscriptions or permanent polling are enabled.
- On Vercel, rate limits use its overwritten `x-vercel-forwarded-for` header. Other hosts must supply a verified trusted-proxy IP adapter; otherwise the application deliberately shares a conservative local rate bucket.

## Launch checklist

Keep `checkout_enabled` and `launch_approved` off until ready. Test-mode checkout can be enabled separately; live checkout additionally requires approved business address, hours, authorised PCN artwork, processing-fee refund treatment, prescription retention and policy text. The owner must also confirm applicable premises/e-pharmacy requirements. Personal pharmacist number 027390 does not establish premises registration.

Approve the privacy, shipping and refund text in Business & checkout. Configure actual delivery zones and estimates; no courier integration or automatic travel-distance calculation is assumed. Verify the Paystack fee schedule and a controlled live payment/refund. Confirm domain/email settings, staff MFA, worker execution, database backups and a restoration exercise before opening checkout.

Do not store prescriptions indefinitely. The retention worker deletes files and metadata from completed/cancelled orders after the configured upload-age threshold. Keep legally required order/payment records according to an owner-approved schedule; implement any jurisdiction-specific retention changes before launch. Customer deletion/access requests go to `support@reliefpointpharmacy.com` and require identity verification.

## Validation and rollback

Run `bun run build`, `bunx tsc --noEmit`, `bun run test` and `bunx playwright test`. Database tests run the migrations and transactional/RLS checks in embedded PostgreSQL with Auth/Storage schemas stubbed; they do not replace staging tests against real Supabase Auth/Storage, Brevo or Paystack. End-to-end provider checks require configured staging credentials.

Before release, test two customer accounts, guest purchase/tracking, staff MFA, browser/session refresh, prescription rejection/refund, duplicate provider events, notification failure recovery and mobile filters. Test real signed uploads against the configured Supabase Storage CORS settings. Monitor HTTP error rates, failed mail/events, oldest pending payment/refund, stock exceptions and Supabase egress in the provider dashboards. Database backups do not by themselves back up Storage file contents: arrange and test separate restricted Storage backups consistent with the approved retention policy.

Rollback application code through the hosting platform's previous deployment. Disable checkout first if payment reconciliation is affected, keep the worker/webhook available, and preserve order/payment history. Do not drop production tables to reverse a release. Restore a backup into a separate project and reconcile provider references before switching traffic.
